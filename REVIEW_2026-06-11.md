# delta-go Analysis & Review — 2026-06-11

Driven by rbackbone's usage (`internal/delta/delta.go`, `pipeline/delta_checkpoint_writer`,
`pipeline/charger`). Library at commit `2bc9f0a` — identical to the version rbackbone pins
(`v0.0.0-20250505155909-2bc9f0a2fdda`), so all findings apply to production behavior.

## Phase 1 — Architecture map

### Table / transaction lifecycle (`delta.go`, 1400 lines)

Two distinct commit paths exist:

1. **LogStore path** (`Transaction.CommitLogStore` → `tryCommitLogStore`, delta.go:903-1052) —
   the delta.io multi-cluster S3 protocol: DynamoDB provides the mutual exclusion that S3
   lacks. Steps: read `Latest` entry from log store → fail if `N.json` exists → recover
   `N-1.json` if its entry is incomplete (`fixLog`) → write actions to temp file
   `_delta_log/.tmp/<file>.<uuid>` → put incomplete entry `E(N)` to DynamoDB with
   `attribute_not_exists(fileName)` (the actual mutex) → copy temp → `N.json` → overwrite
   entry as complete with TTL expiration (+24 h default). **This is the only commit path
   rbackbone uses** (`WriteCommit` → `CommitLogStore` with `MaxRetryWriteAttempts: 1000`,
   nillock as `LockClient`).
2. **Lock + StateStore path** (`Transaction.Commit` → `tryCommitLoop` → `tryCommit`,
   delta.go:1182-1298) — external lock (Redis/DynamoDB/file) plus a version counter in a
   state store. Not used by rbackbone except indirectly via `Table.Create` when no log store
   is configured (rbackbone always configures one).

Concurrency model: a `Table`/`Transaction` is **not** goroutine-safe; safety across processes
comes from the log store conditional put. rbackbone runs one Writer goroutine per pod, many
pods — so cross-pod safety rests entirely on the DynamoDB conditional put + S3 strong
consistency. The `versionLock` in `tryCommitLogStore` (delta.go:974) only reduces duplicate
recovery work; rbackbone passes nillock, which is acceptable per the design comment (duplicate
recovery copies write identical bytes; readers retry on ETag change, delta.go:855-859).

Retry behavior: `CommitLogStore` retries everything except `ErrFailedToCopyTempFile` /
`ErrFailedToAcknowledgeCommit` with a fixed 500 ms sleep (no jitter, no backoff). `ReadActions`
retries with **no sleep at all** (tight loop). `LatestVersion` (delta.go:316-384) probes
versions with `Head` in an exponential-then-binary-search pattern; per call: 1 GET
(`_last_checkpoint`) + O(log gap) HEADs.

### Action serialization (`action.go`, 527 lines)

JSON line per action; `logEntryFromAction` wraps each action in its type key using
`reflect.TypeOf(...).Name()` + strcase (allocation-light; one `map[string]any` + one
`json.Marshal` per action). Reading uses two-stage unmarshal (`map[string]json.RawMessage`
then typed). Allocation churn per commit is dominated by `json.Marshal` of Add stats strings —
acceptable. `Add.Stats` is a pre-marshaled JSON string, so stats are serialized once.

### Stats generation (`stats.go`, 467 lines) — hot path

`NewAdd` (action.go:96) per Parquet file: `Head` (size; up to 2× on zero-size retry) →
`StatsFromParquet` → `NewObjectReaderAtSeeker` (**another Head**, storage.go:327-337) →
`file.NewParquetReader` (arrow-go reads footer via ReadAt: ≥2 ranged GETs). **Total: 4-5 S3
requests per file**; rbackbone calls this once per output Parquet file (millions/day).
The second Head is pure waste — `NewAdd` already knows the size.

### Checkpointing (`checkpoint.go` 515 + `ondiskstate.go` 964 lines)

Write: state rows (protocol, metadata, txns, removes, adds) are paged into ≤50 k-row Parquet
parts, each built fully in a `bytes.Buffer` then `Put`. Read: each checkpoint part is fetched
whole into `[]byte`. With on-disk optimization (`OptimizeCheckpointConfiguration`), add/remove
columns are *not* loaded into the in-memory arrow table (only counted), and part files are
stashed in `_delta_log/.tmp/checkpoint-v<N>-<uuid>/` (the **table's own S3 store** — rbackbone
passes the table store as WorkingStore, so "on-disk" is actually "on-S3"); checkpoint
generation then streams adds/removes back out of those intermediate files part by part. Peak
memory ≈ one full part `[]byte` + its non-add/remove arrow table + one output buffer — the
optimization is real and effective for rbackbone's large tables, at the cost of one extra
Get/Put round trip per part and a re-parse (`countAddsAndTombstones` re-reads the entire part).
Concurrency via errgroup worker pools (`ConcurrentCheckpointRead/Write`), guarded by a single
`concurrentUpdateMutex` for shared state — correct.

### Storage abstraction (`storage/`, `s3store/`)

`ObjectStore` interface; `S3ObjectStore` maps Put/Get/Head/List/Copy+Delete. "Rename" is
CopyObject + DeleteObject (2 calls); `RenameIfNotExists` is Head + Copy + Delete (3 calls,
check-then-act — *not* atomic, by design: atomicity comes from the log store).
All S3 calls use `context.Background()`/`TODO()` — no context propagation, no way to cancel
or deadline anything from the consumer.

### Locks (`lock/*`)

- `nillock` — no-op (rbackbone's commit lock).
- `redislock` — redsync; **no lock extension/heartbeat**, fixed TTL (rbackbone checkpoint
  lock, TTL = `DeltaCheckpointLockTTLMinutes`; rbackbone logs an error if checkpointing used
  >75 % of TTL because the library can't extend).
- `dynamolock` — cirello.io/dynamolock with heartbeat (lease extension exists here but
  rbackbone can't use it for Redis).
- `filelock` — local testing.

### DynamoDB LogStore (`logstore/dynamodblogstore/`)

Items: `(tablePath HASH, fileName RANGE, tempPath, complete, expireTime)`. `Latest` =
consistent Query descending limit 1; `Get` = consistent GetItem; `Put` = PutItem with
`attribute_not_exists(fileName)` unless overwrite. Completed entries get a TTL of +24 h
(`defaultEntryExpirationDelaySeconds`, the documented data-loss guard). **`New()` calls
`CreateTableIfNotExists` → ≥1 DescribeTable on every construction**, and rbackbone constructs
a new LogStore per `WriteCommit`/`GetLastVersion` call — one wasted DynamoDB round trip per
commit batch.

Per `WriteCommit` (steady state): DynamoDB = 1 DescribeTable + 1 Query + 1 GetItem +
2 PutItem; S3 = 1 Head (N.json) + 1 Put (temp) + [1 Head + 1 Copy + 1 Delete] (rename) =
~5 S3 + 5 DynamoDB calls per commit, independent of action count (good — rbackbone batches
many adds per commit).

## Phase 2 — Findings

Severity legend: **CRITICAL** = can corrupt the log / lose data; **HIGH** = wrong results or
production-visible malfunction; **MEDIUM** = correctness edge case, waste, or trap;
**LOW** = polish.

### Correctness under concurrency

**F1. CRITICAL — transient `Head` failure misreported as "already exists", commit falsely
acknowledged.** `s3store.go:142-147` (`RenameIfNotExists`): any non-404 `Head(to)` error
(throttle, 5xx, network, expired creds) falls into `!errors.Is(err, ErrObjectDoesNotExist)` →
returns `ErrObjectAlreadyExists`. In `tryCommitLogStore` Step 3 (delta.go:1041),
`ErrObjectAlreadyExists` is swallowed as "another writer already copied it", and Step 4 then
marks the commit entry **complete** — even though `N.json` may not exist. Subsequent writers
trust the complete entry (delta.go:1004-1010) and commit `N+1.json` without recovery → a
**permanent hole at version N**; Spark/Databricks readers fail the whole table. rbackbone
runs at S3-throttle-prone request rates, so this window is real.
*Fix: only return `ErrObjectAlreadyExists` when `Head` succeeded; propagate other Head errors
(wrapped, retryable).*

**F2. HIGH — `fixLog` defer checks the wrong variable and masks/loses errors.**
`delta.go:1085-1090`: `if unlockErr := versionLock.Unlock(); err != nil { err = unlockErr }`.
Should test `unlockErr != nil`. Consequences: (a) when `fixLog` fails (err != nil) and Unlock
succeeds, the real error is **overwritten with nil** → caller believes the log was fixed when
it wasn't and proceeds to commit on top of a missing `N-1.json`; (b) when Unlock fails after
success, the failure is dropped. (a) is the dangerous half: it can let a writer commit `N.json`
while `N-1.json` is still missing — same hole-in-log failure mode as F1, although it requires
fixLog to fail first (lock contention is enough: `TryLock` error → `ErrLockNotObtained` return
passes through the same broken defer and is nilled out).

**F3. HIGH — `prepareCommit` swallows serialization errors.** `delta.go:1200-1202`: on
`LogEntryFromActions` failure it returns `PreparedCommit{}, nil`. `Commit()` then proceeds to
`tryCommitLoop` with an empty URI; `RenameIfNotExists("", N.json)` behavior is undefined-ish
(on S3: Copy with empty source key → error; on filestore it may copy a directory). Not on
rbackbone's hot path (rbackbone uses CommitLogStore) but on the path used by `Table.Create`
without a log store and by any other consumer using `Commit()`.

**F4. MEDIUM — `TryLock` result ignored in log-store paths.** `delta.go:978` and
`delta.go:1082`: `if _, err = versionLock.TryLock(); err != nil` discards the `locked` bool.
The `Locker` contract allows `(false, nil)` (a custom implementation, or future change);
the code would then proceed *as if locked*. All current in-repo lockers happen to return
`(false, err)` together, so this is a latent trap rather than an active bug. Worth tightening
to `if locked, err := ...; err != nil || !locked`.

**F5. MEDIUM — `LatestVersion` treats any non-404 `Head` error as "commit exists".**
`delta.go:354-362`: the exponential probe `if _, err = Head(...); errors.Is(err,
ErrObjectDoesNotExist) { break } else { count++; ... }` — on persistent throttling this loop
**never terminates** (it keeps advancing maxVersion on every error), and in the binary search
(delta.go:369-382) a transient error flips the direction and silently returns a wrong
`latestVersion`. Wrong latest version feeds `tryCommitLogStore`'s empty-log-store bootstrap
path (delta.go:934-950) → it can put a "completed" entry for a version that isn't actually the
latest. Should distinguish 404 from other errors and return the error.

**F6. MEDIUM — log-store TTL race on `Get` of the previous entry is handled only by retry
luck.** `dynamodblogstore.go:230-231` conflates "item not found" with transport errors
(`err != nil || gio.Item == nil` → same wrapped error with `errors.Join(..., nil)` dropping
detail). In `tryCommitLogStore` Step 1 (delta.go:1004), a `Latest`→TTL-deletion→`Get` race
returns this error and burns a retry attempt; fine at 1000 attempts, but the error string
("failed to get item" with no cause) makes production triage needlessly hard. Also unchecked
type assertions in `mapItemToEntry` (dynamodblogstore.go:271-282) **panic** if another client
wrote an item without `tempPath` (the delta-spark S3DynamoDBLogStore schema stores different
attributes!) — interop with Spark's `S3DynamoDBLogStore` on the same table would panic, not
error.

### Protocol compliance

**F7. HIGH (known, now confirmed) — reader/writer version ceiling is v1/v1, enforcement
scattered, consumer must use unsafe flags.** `delta.go:40-41` caps support at reader 1 /
writer 1, yet `Table.Create` happily writes protocol v3/v7 tables with
`variantType-preview` features (rbackbone delta.go:263-276) and then returns an error the
consumer must ignore. Checkpointing those tables requires
`UnsafeIgnoreUnsupportedReaderWriterVersionErrors`. The table state *does* track
Reader/WriterFeatures (tablestate.go:57-58, preserved through checkpoints since #339).
What's missing is a *feature-aware* gate: blind appends + checkpoints are safe on tables whose
features are append-compatible (e.g. `appendOnly`, `invariants` unused by data,
`variantType-preview` where writer only appends pre-validated Parquet), and the library should
expose an allowlist (`SupportedFeatures`) instead of a single unsafe boolean. (Larger design
item — flagged, not fixed in this pass.)

**F8. MEDIUM — `IsVersionWrittenByDeltaGo` logic belongs in the library.** rbackbone
re-implements client-version sniffing (rbackbone internal/delta/delta.go:196-228, marked
TODO "move into delta-go"). The library writes `clientVersion: delta-go.alpha-0.0.0`
(delta.go:39, 206, 1157) but offers no reader for it. Add `Table.VersionIsByClient(version)`
/ expose `CommitInfo.ClientVersion()` helper.

**F9. LOW — `clientVersion` constant is stale** (`alpha-0.0.0`, delta.go:39) — every commit
in production self-identifies as alpha. Cosmetic but visible in Databricks history output.

### Hot-path performance

**F10. HIGH — `NewAdd` performs a redundant S3 Head per file.** `action.go:109` does
`store.Head(location)` to get size; `StatsFromParquet` → `NewObjectReaderAtSeeker`
(storage.go:331) does **another Head of the same object**. At rbackbone's volume that is
millions of wasted S3 requests/day (~20-25 % of the per-file request budget).
*Fix (back-compatible): add `NewObjectReaderAtSeekerWithSize(location, store, size)`; thread
`add.Size` through `StatsFromParquet`.*

**F11. MEDIUM — `NewAdd` zero-size retry is broken by a reversed `errors.Is`.**
`action.go:110`: `errors.Is(storage.ErrObjectDoesNotExist, err)` — arguments swapped, so a
*wrapped* not-exist error (which is what s3store returns, s3store.go:201) never matches: a
genuinely missing file falls through, retries Head once, then returns `ErrAddZeroSize`
instead of `ErrObjectDoesNotExist`. Also, real Head errors (throttle) are silently converted
to `ErrAddZeroSize`, which rbackbone logs as a stats problem instead of retrying. Misleading
prod telemetry.

**F12. MEDIUM — `ReadActions` retry loop has no sleep** (`delta.go:866-886`): on S3 throttle
it spins `MaxRetryReadAttempts` (3) times back-to-back, guaranteeing failure on a throttled
prefix and adding fuel to the throttle. Add the transaction's `RetryWaitDuration`.

**F13. MEDIUM — every `dynamodblogstore.New` performs `DescribeTable`** (CreateTableIfNotExists,
dynamodblogstore.go:200), and rbackbone constructs one per commit batch. Add
`Options.SkipTableCreation` (or cache table-exists status per table name, process-wide) so
steady-state commits skip the extra round trip.

**F14. LOW — `CommitLogStore` fixed 500 ms retry with no jitter/backoff** (delta.go:921,
defaults delta.go:1313-1318): under contention (many pods, same table) all writers retry in
lockstep. Exponential backoff + jitter materially reduces conflict rounds; with rbackbone's
`MaxRetryWriteAttempts: 1000` the worst case is 8+ minutes of synchronized hammering.

**F26. MEDIUM (found during implementation) — `setOptionsDefaults` never defaults
`RetryWaitDuration`.** delta.go:132-148: consumers that construct `TransactionOptions`
directly (rbackbone passes `TransactionOptions{MaxRetryWriteAttempts: 1000}`,
rbackbone delta.go:308) get a **zero** retry wait — `CommitLogStore` hot-loops its retries
with no sleep, hammering S3/DynamoDB during commit contention. Fixed by defaulting to 500 ms.
**Behavior change for rbackbone**: contended commits now back off 500 ms between attempts
instead of spinning; total worst-case retry time rises from ~instant-fail to bounded waiting,
which is the intended design of the retry loop.

**F27. MEDIUM (found during implementation) — `ObjectStore.ReadAt` had two contradictory
`max` conventions.** `ObjectReaderAtSeeker` passed an exclusive end offset; the s3store
implementation and its tests treated `max` as an inclusive index (`bytes=off-max` header,
s3store.go:362). Net effect: every ranged S3 read over-fetched one byte, and a read ending
exactly at the object boundary relied on S3 tolerating an over-long range. Standardized the
contract as exclusive end (documented on the interface), corrected the Range header to
`max-1`, and updated the s3store tests to the clarified contract.

### API ergonomics

**F15. MEDIUM — no lock extension on `lock.Locker`** (the known gap, rbackbone delta.go:111).
redsync supports `Extend()`; the interface doesn't expose it. Long checkpoints (rbackbone
warns at >75 % TTL, rbackbone delta.go:163-165) risk a second writer entering mid-checkpoint.
Minimal fix: optional `lock.Extender` interface (`Extend() (bool, error)`) implemented by
redislock; checkpoint loop extends between parts. (Implemented for redislock in this pass;
wiring into `CreateCheckpoint` left for a follow-up since part boundaries are inside
generatePart workers.)

**F16. MEDIUM — `Get`/`Latest` error taxonomy.** `logstore` defines only
`ErrLatestDoesNotExist`; `Get` not-found needs its own sentinel so callers can distinguish
"expired/never existed" from "DynamoDB is down" (see F6).

### Robustness

**F17. MEDIUM — `parseInterval` month/year are wrong by 7×.** `config.go:117-122`:
`month = 24×7×31 h` (≈217 d), `year = 24×7×365 h` (≈7 y) — a stray `×7` copied from the week
case. Affects `delta.deletedFileRetentionDuration` / `delta.logRetentionDuration` parsing:
tombstones and logs retained ~7× longer than configured (bloats checkpoints/log listing; the
"safe" direction, but wrong and surprising). Spark's CalendarInterval treats month = 30 d,
year = 365 d.

**F18. MEDIUM — `truncatedStringStat` panics on multi-byte strings.** `stats.go:357-376`:
`if len(s) >= 32` (bytes) then `r := []rune(s); r[32:]` — a string with ≥32 bytes but <32
runes (e.g. 20 CJK chars) panics with slice out of range. `NewAdd` has no recover; in
rbackbone the panic would take down the Writer goroutine processing loop. VINs are ASCII but
signal/string columns are not guaranteed to be.

**F19. MEDIUM — `formattedTimestampStat` silently returns the zero time for
`TimeLogicalType`** (`stats.go:401-402`: empty case bodies fall through to formatting
`time.Time{}`) → stats record `0001-01-01T00:00:00.000Z` min/max instead of an error.
Data-skipping correctness: a Spark query pruning on such a column could skip files
incorrectly? No — min below any real value / max below too… max of zero-time **understates**
the true max → **files can be wrongly pruned** for predicates like `ts > X`. (Edge: only for
TIME-typed columns routed through the timestamp function; rbackbone schemas don't use TIME.)

**F20. MEDIUM — `ObjectReaderAtSeeker.Read` never advances the offset** (storage.go:352-358):
sequential `Read` calls return the same bytes forever (io.Reader contract violation). Arrow's
parquet reader uses ReadAt/Seek so today it's dormant, but any consumer wrapping the reader in
`bufio`/`io.ReadAll` gets an infinite loop.

**F21. LOW — `prepareStateForCheckpoint` extended-file-metadata logic is dead code.**
`tablestate.go:522-527`: `doNotUseExtendedFileMetadata` initialized `false` then only ever
`&&`-ed — stays false forever. Intent (per on-disk twin `prepareOnDiskPartStateForCheckpoint`,
ondiskstate.go:687: uses `||`) is "if ANY tombstone lacks extended metadata, strip it from
all". In-memory path never strips → checkpoint can mix extended/non-extended tombstones.

**F22. LOW — `checkpointRows` off-by-one drops a Txn at a part boundary.**
`tablestate.go:605`: Txn rows use `startOffset < currentOffset+i` where the Remove/Add
sections use `<=`. A multi-part checkpoint whose part boundary lands on the Txn block skips
one Txn row → `ErrCheckpointRowCountMismatch` aborts the checkpoint (fail-safe, but a real
checkpoint-availability bug for tables with app transactions).

**F23. LOW — no context propagation anywhere** (`context.Background()`/`TODO()` in s3store,
logstore, checkpoint errgroups). Consumers cannot time-bound a commit or checkpoint. API
addition (`...WithContext` variants) — flagged for a dedicated pass, not done here.

**F24. LOW — `dynamolock.New` creates a malformed table on first use**: `dynamolock.go:97-109`
builds `CreateTableInput` with `AttributeName: aws.String(string(key))` — the *parameter*
`key` (the lock path) shadows the package const `key = "key"`, and `AttributeDefinitions` is
missing entirely, so CreateTable always fails validation; `CreateTableIfNotExists` then spins
20 attempts and errors. Only hit when the lock table doesn't pre-exist (rbackbone unaffected).

**F25. LOW — `CreateTableIfNotExists` logs RCU twice** (dynamodbutils/dynamodbclient.go:67:
both placeholders use `ReadCapacityUnits`), and treats *any* DescribeTable error (e.g.
AccessDenied, throttle) as "table does not exist" → spurious CreateTable attempts.

### rbackbone-side notes (not library changes; for the TODO file)

- `WriteCheckpoint` `tableCache`/`recover()` swallows panics — after F18 fix, consider
